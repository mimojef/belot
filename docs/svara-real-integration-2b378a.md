# Свара — Етап 2Б.3.7.8А

## Установена причина

Блокерът беше погрешен избор на backend процес от теста, а не отказ на правилно конфигурираната изолирана регистрация.

Преди непроменения harness на `0.0.0.0:3001` вече слушаше друг локален Node backend. Старият harness:

1. Проверяваше свободен порт чрез bind към `127.0.0.1:3001`. Под Windows този bind може да успее при вече съществуващ wildcard listener на същия порт. Това е възпроизведено с два собствени, временни TCP сървъра.
2. Стартираше нов backend и чакаше само неговото съобщение за завършена SQLite миграция. То се отпечатва **преди** `httpServer.listen()`.
3. След това приемаше `/health` от фиксирания порт за доказателство за готовност. На него отговаряше вече работещият процес, а не child-ът с новата тестова база.
4. Изпращаше и HTTP регистрацията към този чужд за теста процес. Неговият `authStore.register()` връщаше „Регистрацията временно не е налична.“ от guard-а за невалидно конфигуриран регистрационен secret. Настройката `direct` и валидният тестов secret бяха за **другата**, новосъздадена база/процес.

Допълнително `tsx` CLI е обвивка около действителния server child. Спирането само на обвивката не е надеждно доказателство, че HTTP listener-ът е спрян. При някои от предходните неуспешни Windows изпълнения имаше и Node/libuv `UV_HANDLE_CLOSING` assertion. Новият harness притежава директния Node процес.

Не е спиран чуждият backend и не са променяни неговите настройки или база.

## Решение в тестовата инфраструктура

- Backend-ът използва съществуващия `PORT=0`: портът се избира атомарно от ОС. Тестът не използва 3001.
- Изпълнява се пресен компилиран backend чрез директен Node child. Копират се само `src`, `dist`, миграциите и package metadata в нова `mkdtemp` директория; няма копиране на `.env`, accounts или база. Source mtimes са запазени за непроменената production worker freshness проверка.
- Средата на backend-а е от бял списък. Не се наследяват production secrets, DB URL, dotenv overrides, `NODE_OPTIONS`, payment/campaign флагове. Използва се нов локален регистрационен secret с достатъчна дължина.
- Частен bootstrap, създаден само във временната директория, съобщава PID, parent PID, nonce и действителния listening socket по родителски IPC канал. `/health` се проверява само след това и след съобщението за **точния** SQLite файл. Няма публичен test endpoint.
- Bootstrap-ът не е Node preload за worker threads и не заменя техния production код. Не променя RNG, часовник, runtime, команди или авторизация. При загуба на родителя child-ът приключва, включително ако server signal handler още не е инсталиран.
- Само локален gateway на друг OS-assigned порт обслужва production frontend build-а и препраща HTTP/API и истинските WS upgrades към доказания backend. Използва се `svara-integration.localhost`, за да се упражни съществуващият production same-origin кодов път, без промяна на hardcoded development URL в клиента.
- HTTP тела, Origin и cookies се препращат без подмяна; WS frames не се конструират или инжектират. Chromium не може да изпраща HTTP заявки към външни услуги или production API през този harness.

Двата профила се създават с реални HTTP регистрации в съществуващия `direct` режим, конфигуриран само в собствената тестова база. Създадените profile/session редове се сверяват с HTTP отговорите. Тестовата роля `admin` се задава само на тези два реда по вече използвания fixture подход от restart тестовете. След това реалният backend проверява реалните cookies, сесии и роли при HTTP и WS достъп. Няма production backdoor или отслабена регистрационна проверка.

## Реален браузърен сценарий

Два независими Chromium context-а използват различни реални cookies и профили. Създаването на масата, join/leave/rejoin, стартът, „Погледни“, първият залог, следващото повишаване и отказът се управляват през истинския интерфейс. Проверени са също reload и връщане след навигация, без ново присъединяване или плащане.

I1–I6 добавят доказателства за:

- Липса на стари test profiles и match snapshots в новата база.
- Два различни HTTP профила и активни session редове именно в нея.
- Реалните Входове: по един ledger entry на играч, точно намаление на началния стек и вноски преди първия ход.
- Реално сървърно `dealing` състояние; без betting бутони преди края му.
- Получените от браузърния WS snapshots са идентични с разрешената индивидуална проекция от същия запис в SQLite. DOM ревизията, показаните стекове и разрешените card image sources се сверяват с тях.
- След „Погледни“ се виждат точно трите разрешени собствени карти; противниковите лица не се появяват без разрешен публичен показ.
- Реален залог и реално следващо действие от двамата играчи, без самостоятелна клиентска промяна на балансите.
- Приключване на browser contexts, gateway sockets, действителния Node backend и неговия listener; премахване на собствената временна база. Junction-ите се откачат преди рекурсивното премахване, а target paths се проверяват спрямо собствената temp директория.

Сценарият използва истински часовник и произволно сървърно разбъркване. Няма mock snapshots, raw WS gameplay injection, подменени cards/stacks или замразени deadlines. Всяка съществена проверка е fail-fast; няма автоматичен retry на провален сценарий или игнориране на грешки, за да се получи зелен резултат. Съществуващото ограничено изчакване за реални async DOM/snapshot преходи е запазено.

## Проверки и обхват

Окончателният real Chromium harness е изпълнен в предварително зададена последователност от **три пълни изпълнения**, спираща при първи провал. Всяко използва нов child, портове, профили и SQLite файл. Резултат: **24/24 във всяко изпълнение**.

`checkSvaraRealIntegrationHarness.ts` проверява отделно 8 инфраструктурни защити: wildcard port collision, изолацията на environment, чужд PID/nonce/parent, опасни cleanup paths, невъзможна активация на test hook в production/без IPC/с чужд parent и приключване при прекъснат parent преди startup.

Допълнителни резултати:

- Инфраструктурни защити: **8/8**.
- Реални lobby/WS проверки: **14/14**, включително разрешени и забранени роли, подправена/отнета сесия, понижаване на роля, feature flag OFF и поверителност на изпратените данни.
- Snapshot security: **20/20**; lifecycle: **29/29**; client lobby/lifecycle: **17/17**.
- Access: при първото паралелно изпълнение **35 успешни / 2 неуспешни** — остаряла UI проверка B7 и worker startup timeout (5000 ms). Отделно диагностично изпълнение без паралелен build: **54 успешни / 1 неуспешна**. Всички действителни HTTP authorization проверки преминаха; B7 продължава да очаква старото placeholder съдържание „В разработка“. Този стар скрипт не е обявен за изцяло успешен и не е променян.
- Допълнителният непроменен restart скрипт: **5 успешни / 1 неуспешна**, след което fail-fast прекратява останалите сценарии. На `checkSvaraRestart2B36C.ts:415` веднага след последното плащане очаква `svara-joining`, но актуалният engine първо отваря `showdown-display`. Скриптът няма обработка за тази междинна фаза. Не са променяни gameplay или този стар сценарий за получаване на зелен резултат; неговият собствен порт е освободен след прекратяването.
- TypeScript за клиент/сървър/трите тестови TypeScript файла, production Vite/PWA build и `git diff --check`: успешни. Build-ът показва съществуващото предупреждение за размер на chunks.

Старият engine провал остава отделен: **86 успешни и 1 неуспешен H2**, защото `git grep games/svara/engine -- src` брои коментари в два клиентски файла като imports. Проверката и engine правилата не са променяни.

Това възстановява реалната инфраструктура и основния двуиграчен сценарий. Пълната матрица от 2Б.3.7.8Б не е започвана. Няма SSH, VPS промени, production deploy или промени по gameplay, SQLite схема, други игри и реални жълтици.
